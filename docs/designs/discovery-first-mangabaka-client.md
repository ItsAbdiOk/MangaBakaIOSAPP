## Problem Statement

Finding something new to read on MangaBaka currently means going to the desktop
website. There is no way to browse for a next read on a phone, which is where
that browsing actually happens — in dead time, away from a desk.

The app's center of gravity is **discovery**. Broad feature parity with the
website is the ambition, bounded by what the API exposes.

## What Makes This Cool

Four discovery shapes, all wanted, all supported by public endpoints:

1. **Browsable home feed** — one scrollable surface mixing rising, hidden gems,
   news, and top genres. Open with no goal, always leave with something.
   (`/v2/series/discover/rising`, `/v2/series/discover/hidden-gems`,
   `/v1/series/mix`, `/v2/news`, `/v0/frontpage/community-pulse`)
2. **Swipeable next-read stack** — one series at a time, cover-forward, save or
   skip. Phone-native; the website has no equivalent. Turns a bus ride into a
   triage session.
3. **Deep rabbit-holing** — from any series jump to similar, readers-also-like,
   related, same collection, same publisher, same tags. Discovery by wandering.
   (`/v1/series/{id}/similar`, `/readers-also-like`, `/related`, `/collections`,
   `/links`, `/relationships`)
4. **Saved-for-later shelf** — discovery is worthless if you forget what you
   found. Fast "maybe later" bucket, later synced to the MangaBaka library.

**No backend.** The app talks to MangaBaka's API and stores its cache on the
user's own device. There is no server to run and no user data held by the
developer.

The unifying insight: all four want data to already be there. A card that
spinners is a card you skip. That is what makes the on-device cache the
foundation rather than an optimization.

## Constraints

**Licence (verified at https://mangabaka.org/api):**
- MangaBaka-original data is **CC BY-NC-SA 4.0** — personal and non-commercial
  use, with attribution. Commercial use requires separate terms.
- Attribution to MangaBaka **and** the underlying data providers is mandatory.
  Providers are enumerable from `/v1/source/*`: AniList, Kitsu, MangaUpdates,
  MyAnimeList, Anime-Planet.
- Decision: the app is free forever. No ads, no IAP, no paid tier. Attribution
  ships as a real screen, not a buried footnote.

**Rate limits (same source):**
- 30 req/min for search, 180 req/min default.
- **Per IP**, leaky bucket. Users behind the same carrier NAT share a budget.
- **Cached responses do not count.** MangaBaka's own CDN caches most discovery
  endpoints for a day or more (`x-cache-ttl-cdn-seconds`: 86400 on rising,
  hidden-gems and readers-also-like; 604800 on `/v1/series/batch`).
- Library writes are `x-cache-ttl: NO_CACHE`, so every write costs budget.
- See "Request budget" below — the arithmetic, not the vibe.

**Auth (verified at https://mangabaka.org/.well-known/openid-configuration):**
- `authorization_code` + PKCE `S256` + `refresh_token` + `offline_access`.
  Native-app friendly: `ASWebAuthenticationSession`, no client secret.
- Scopes: `library.read`, `library.write`, `mod`, `openid`, `profile`,
  `offline_access`.
- **No `registration_endpoint`** — no dynamic client registration. A `client_id`
  must be issued by a human at MangaBaka. No published process for obtaining one.

**API shape:**
- 51 of 77 operations are public (no auth). **Every discovery endpoint is
  public.** Auth gates only `/v1/my/*` and `/v2/my/library` (library, profile,
  personalized recommendations, personalized top-genres),
  `/v0/my/submissions/*`, and `/mod/*`.
- v1 and v2 coexist for search, series, batch, similar, readers-also-like. The
  spec does not say which is canonical. Unresolved — see Open Questions.
- All responses share a shape: `status` root key always; `message` on errors
  (safe to show users verbatim); `pagination` when paginated; `data` as object
  for single resources, array for collections.

**Distribution:** open source, App Store eventually. Privacy manifest and
third-party asset licences are live requirements, not deferrable.

## Approaches Considered

### Approach A: Thin client, ship fastest
Direct API calls per screen, no cache layer, local-only shelf, no auth.
Effort: human ~1wk / CC ~1d. Risk: Low. Completeness 6/10.
Rejected: not on rate-limit grounds — the Request budget section below shows
the swipe stack was never close to the cap. Rejected because every screen would
show a loading state on every visit, nothing would work offline, and the cache
would be retrofitted later anyway, against code that had assumed it away.

### Approach B: Auth-first parity client
OAuth and library sync as the core, discovery layered on top.
Effort: human ~3wk / CC ~3d. Risk: High. Completeness 10/10 but wrongly ordered.
Rejected: builds the one externally-blocked part before the 51 endpoints that
are not blocked.

### Approach C: Offline-first repository core (CHOSEN)
A local cache is the foundation. To be explicit, because the word "database"
caused confusion in session: this is a file on the end user's own device, not a
server. The app has no backend, stores nothing about anyone anywhere, and the
developer never has access to any user's data. The cache exists so the app does
not re-download what it already has — the same role a browser cache plays.

Every screen reads from that cache; the cache decides when to hit the network.
Discovery, prefetch and offline become one problem. Auth is a capability the
repository gains later, not a foundation it rests on.
Effort: human ~4-6wk / CC ~4-5d. Risk: Med. Completeness 9/10.

## Recommended Approach

**Approach C, PAT-backed and OAuth-ready.**

Effort caveat: the ~4-5 CC-day figure covers everything this document now
specifies — repository core, `TokenProvider`, four discovery surfaces, the
failure and offline states, and the testing strategy including golden fixtures
and clock-injected cache tests. It is an estimate with no measurement behind it
and should be treated as a guess until the first milestone lands and gives a
real rate. The A/B/C figures were revised upward after the scope was written
out in full; the original numbers were made before those sections existed.

Rationale: the cache delivers instant navigation and offline browsing, which
matters precisely when people browse manga (commute, no signal). It also keeps
request volume low, though — see below — the budget was never the binding
constraint for the swipe stack.

### Request budget

Doing the arithmetic changed the argument, so it is recorded here rather than
asserted. Page sizes are from the spec, not estimated:

| Endpoint | `limit` default / max | CDN TTL |
|---|---|---|
| `/v1/series/mix` | 24 / **50** | varies |
| `/v2/series/discover/rising` | 12 / 20 | 1 day |
| `/v2/series/discover/hidden-gems` | 12 / 20 | 1 day |
| `/v1/series/{id}/readers-also-like` | 12 / 24 | 1 day |
| `/v1/series/batch` | **50 series per request** | 7 days |

A ~100-card swipe session therefore costs about **3 to 5 requests**: one `mix`
at `limit=50`, `rising` and `hidden-gems` at `limit=20`, and one `batch` call to
hydrate up to 50 series at once. Against 180 req/min — or even 30 — that is not
close to the cap, and the day-long CDN TTLs mean repeat sessions cost less
still.

**So the earlier framing was wrong.** An earlier draft called the rate limit the
central architectural fact and justified the cache by it. The numbers do not
support that for the swipe stack. The cache earns its place on latency and
offline behaviour; the request budget is a secondary benefit.

**The real rate-limit risk is typed search.** 30 req/min is one request every
two seconds sustained, and search-as-you-type fires per keystroke. Debouncing
the search field is the actual mitigation, and it is a UI concern, not a cache
concern.

**Never hydrate a feed with N individual `GET /series/{id}` calls.** Use
`/v1/series/batch` (50 per request, cached 7 days). This is the single highest-
leverage rule in the networking layer.

Two caveats, both unverified: it is not documented whether the discovery
endpoints draw from the 30/min "search" bucket or the 180/min default one, and
cover images are assumed to be CDN assets that do not consume API budget at all.
Both are cheap to measure once there is a running app; neither is assumed
favourably above.

Two design commitments make the eventual PAT to OAuth migration cheap. Both
cost roughly nothing to adopt now; the first is genuinely expensive to
retrofit, the second is merely tidier done early:

1. **`TokenProvider` protocol.** Auth is one protocol with two implementations.
   `PATTokenProvider` sets `x-api-key: mb-…` today; `OAuthTokenProvider` sets
   `Authorization: Bearer …` later. Call sites never change.
2. **An owner column on the personal tables only.** Library, saved shelf, and
   personalized recommendations carry a user id; the public catalog cache
   (series, covers, feeds, tags, genres) does not, because that data is
   identical for everyone and scoping it would force a full re-download after
   any sign-out. The column exists so that signing out and signing in as
   someone else on the same phone does not show the previous person's list.
   Cheap insurance against one bug, not architecture — skipping it costs an
   afternoon later, not a rewrite.

What the migration still costs, and is not a "swap": PATs never expire, OAuth
access tokens do. Adding OAuth means adding refresh-token rotation,
retry-on-401, and Keychain storage. Contained and well-understood, but it is
new code, not a header change.

**Credential rule:** the PAT is a real credential for the user's own account.
It lives in a gitignored `Secrets.xcconfig` or Keychain, never in the repo, and
never in a TestFlight or App Store build. Anyone with the binary can extract an
embedded token and act as that account.

## Technical Choices

- **UI: SwiftUI.** No reason to reach for UIKit here; the screens are lists,
  grids, a card stack and a detail view.
- **Deployment target: iOS 26+.** Decided, not a guess. The app commits fully
  to Liquid Glass, so there are no fallback visual paths and no second design
  language to maintain. This deliberately trades reach for the look; the look
  is the point.
- **Persistence: GRDB (SQLite).** Chosen over SwiftData because Liquid Glass
  spends the GPU budget on live refraction and blur during scroll, which leaves
  the data layer needing to be predictable rather than convenient. GRDB fetches
  exactly what is asked for, keeps memory flat, makes TTL columns and indexes
  explicit, and unit-tests without standing up a container. SwiftData's faulting
  and change-tracking do work that cannot be inspected when a scroll stutters.
  The cost is more code, which is acceptable here.
  **Unmeasured:** this is architectural reasoning, not a benchmark. If a scroll
  ever stutters, measure before re-litigating.
- **Networking: `URLSession` plus `Codable`, no third-party HTTP client.** The
  response envelope is uniform enough (`status` / `message` / `pagination` /
  `data`) to wrap in one generic decoder.
- **`mangaupdates_openapi.json` is reference only.** MangaUpdates data reaches
  the app through MangaBaka's `/v1/source/manga-updates/{id}` passthrough. The
  app does not call MangaUpdates directly. Calling it directly would mean a
  second set of terms, rate limits and attribution obligations, for data
  MangaBaka already provides. Kept in the repo for cross-referencing IDs.

## Failure and Offline Behaviour

Not an afterthought; these are the states the user will actually hit.

- **Rate limited (HTTP 429).** Back off and serve from cache. The user should
  see stale content with a quiet "updated N minutes ago", never an error.
  Because the limit is per IP, a user can be limited by someone else's traffic
  on the same network — so this must never read as the user's fault.
- **Offline.** Home feed, previously-viewed series, and the saved shelf render
  from cache. Anything uncached shows an explicit offline state, not a spinner
  that never resolves.
- **Empty results.** Search with no matches, a series with no
  readers-also-like, an empty shelf — each gets a designed state, not a blank
  screen.
- **Malformed or partial responses.** Decode failures are caught per item, not
  per page: one bad series in a batch of 50 must not blank the feed.
- **Errors are named, not swallowed.** No catch-all that maps every failure to
  "Something went wrong". The API returns a `message` field that is documented
  as safe to show users verbatim — use it.
- **Cover image failures** get a placeholder, never a broken layout.

## Testing Strategy

Aligned to the standards in CLAUDE.md.

- **Golden fixtures.** Record real API responses to disk and decode against
  them. Cheap, deterministic, and they catch schema drift when MangaBaka
  changes something.
- **A control fixture with a known answer** in every decode suite, so a broken
  harness announces itself rather than passing silently.
- **A request-budget test.** Simulate a 100-card swipe session against a
  recording layer and assert the request count stays under the stated bound.
  This turns a success criterion into something measured rather than believed.
- **Cache expiry tests** driven by an injected clock, not `sleep`.
- **Failure-path tests** for each state in the section above — 429, offline,
  empty, malformed. A test that only exercises the happy path proves the happy
  path.
- **Before/after numbers on any performance claim.** No fix lands with "feels
  faster" as its evidence.

## Open Questions

1. **v1 vs v2.** Both are live for search, series, batch, similar, and
   readers-also-like. v2 additionally holds `discover/rising` and
   `discover/hidden-gems`, which suggests v2 is the forward path — but the spec
   does not say, and v1 has endpoints v2 lacks (`mix`, `works`, `collections`,
   `publishers`, `editions`, `tags`). Needs a decision before the repository
   layer hard-codes paths. Not confidently answerable from the spec alone.
2. **Does ShareAlike reach the app?** Best reading is that CC BY-NC-SA's SA term
   attaches to the data and to adaptations of it, not to Swift code that merely
   queries the API — so the app's own licence is the user's choice. If the app
   ever ships a bundled derived dataset, SA plausibly does bite. **Not a
   confident verdict; worth asking MangaBaka or a lawyer before release.**
3. **Does a free App Store app satisfy "non-commercial"?** Almost certainly, but
   MangaBaka defines the term, not this document.
4. **Will MangaBaka issue a `client_id` to a third-party client?** No published
   process. Unknown until asked.
5. **Cache freshness policy.** Which endpoints tolerate stale data and for how
   long? The spec's per-endpoint `cache ttl` annotations are the input; they have
   not yet been extracted systematically.
6. **Per-IP rate limiting under carrier NAT.** Two users on the same mobile
   network share the 30/min search budget. Unclear how often this bites in
   practice; needs measurement, not speculation.

## Success Criteria

- Open the app cold with no goal and find something worth reading, without
  typing a search.
- The swipe stack advances with no visible loading state under normal use.
- The home feed and previously-visited series render offline.
- Search-heavy browsing never trips the 30 req/min cap during ordinary use.
- Attribution to MangaBaka and every upstream provider is present and correct.
- Swapping `PATTokenProvider` for `OAuthTokenProvider` requires no changes at
  any API call site. The token provider itself gains real new logic (refresh
  rotation, retry-on-401, Keychain) — that is expected, not a failure.
- A simulated 100-card swipe session issues no more than 6 API requests.
- No force-unwrap anywhere on the path from network response to view.
- Scrolling holds 120fps on ProMotion hardware with Liquid Glass active.
- Memory stays flat while scrolling an unbounded feed — the cache evicts, and
  scrolling forever does not grow the heap without bound.
- No measurable battery cost from background or idle work; the app does nothing
  when not on screen.

## Distribution Plan

- Open-source repository at github.com/ItsAbdiOk/MangaBakaIOSAPP (public).
- App Store eventually. Requires before submission: privacy manifest
  (`PrivacyInfo.xcprivacy`), third-party font and asset licences cleared,
  attribution screen, and confirmation that a free third-party client is
  permitted under MangaBaka's terms.
- No analytics or telemetry of any kind without an explicit, separate decision.
  No third-party endpoints.
- CI: not yet decided. GitHub Actions running build and tests on PR is the
  obvious default; no release automation needed until there is something to
  release.
