# Search tab — live simulator walk

Device: iPhone 16 Pro simulator, UDID B963E62F-F657-4C7F-AF7A-CCF9E6C8DCF0, app `dev.abdirahmanmohamed.mangabaka` (already built/installed — not rebuilt for this walk). Screenshots referenced below live in this session's scratchpad under `search-walk/` (not committed to the repo; numbered filenames match the order taken). All findings below are **observed** on-device unless explicitly marked **guessed**.

Note up front: the live UI does not match the brief's description of `SearchIdleView` (it describes a Tags/Genres/Publishers-first panel with a "your saved lenses" list of *preset* lenses). What's actually on screen is a fuller filter builder (Type/Status/Sort/Minimum rating/Year/Narrow-by/Offline toggle) inline under Recent searches, plus a "Browse" / "Surprise me" pair of buttons. This is simply newer than the brief anticipated — noted so the reader doesn't think I misread the screen.

## 1. First-time reader: cold open

- Screenshot `01-search-idle-cold.png`: tab opens to a search field ("Title, author, or tag" placeholder — good, it tells you what you can type), a "Browse" / "Surprise me" button pair, a "Recent" list of 3 prior searches, then an inline filter builder (Type, Status, Sort, Minimum rating, Year, Narrow by: Tags/Genres/Publishers, Offline toggle). It's a lot to take in on first open — nothing above the fold hints that scrolling reveals a full filter builder, but it isn't confusing exactly; it reads as "search box + browse shortcuts + history", which is a reasonable mental model. Not obviously broken, not obviously delightful.
- **Tags** button (`03`/`03b-tags-tap-t1s.png`): opens a sheet instantly (no visible delay between t0 and t1s screenshots — either it's pre-fetched or fast enough that this test can't distinguish). Categories are collapsible (Activities 126, Audience Demographics 3, Character Archetype 112, Character Traits 14, …) with a "Search 500 tags" box at the top — a real search-within. Expanding "Activities" (`04-tags-activities-expanded.png`) shows only 8 of 126 with a "118 more in search" hint pointing at the search box — a nice, deliberate affordance, not a bug.
- **Genres** button (`07-genres-sheet.png`): opens instantly too, but is a flat, uncategorized list of ~50 chips with **no search-within box** and **no count badges**, unlike Tags. Inconsistent design between two sibling pickers reached from the same row.
- **Bug, high confidence** — tapping a tag or genre chip directly (the "obvious" fast path: tap category button → tap a chip) immediately dismisses the sheet and jumps to the results screen showing **"0 shown / Nothing matched these filters"**, for both a Tags pick ("Working", screenshot `05-tag-working-selected.png`) and a Genres pick ("Action", screenshot `08-genre-action-tapped.png`). Reopening the **Filters** sheet from that exact same broken state shows the filter really is set correctly (`Genres: 1` badge) and its own live count says **"Show 4,260 results"** (`11-filters-sheet-scrolled.png`) — tapping that button does correctly render 30 (then paginating to 120+) real results (`13b`, `16-showresults-attempt3.png`). So: the direct chip-tap path and the Filters-sheet "Show N results" path apply the identical filter, but only one of them renders it. The direct-tap path is the one a first-time reader is most likely to use, and it looks completely broken (empty state, no retry affordance visible without leaving the dead-end results screen). **Where**: the chip-selection commit path in whatever view backs the inline Tags/Genres picker vs. `FilterPanel`'s "Show results" action (not confirmed against source — this is a runtime observation only, no line cited).
- Filter persistence: reopening Filters after the Genre pick showed the badge and count still applied (`17`, `18-filters-scrolled-clearall.png`). "Clear all" resets it cleanly, with an "Undo clear" affordance appearing immediately after (`19-after-clearall.png`) — a nice touch.
- **Gap, likely real**: after clearing the query text with the field's `×`, an active **Type** filter (e.g. "Manga") silently survives and the results grid keeps showing a filtered (unlabeled) browse list instead of returning to the true idle screen (Recent + Browse/Surprise me) — see `43-idle-check-lens.png` vs `44-filters-check-manga-persist.png`, where reopening Filters shows "Manga" still selected. The "Filters" button itself carries **no badge/dot** indicating a filter is active, so there is no visible cue on the main screen that you're not looking at neutral trending content.

## 2. Typing reader: "one piece" character by character

- Typing `o` alone (`23-type-o-t0.png`, `23b` at +1s): the grid shown does **not** reflect the letter "o" at all — titles like "X", "C³", "Magi…" contain no "o". This is the generic Browse/trending list rendered under a "30 shown" label as if it were search output, with the query box showing my typed `o`.
- Typing `on` (`24b-type-on-t1s.png`): results now genuinely match ("On", "One-Punch Man", …) — so the actual query kicks in somewhere between 1 and 2 characters.
- Confirmed the same pattern isolated: typing `a` alone (`63-onechar-a.png`, task 3) shows "30 shown" with titles "X", "C³", "Pi", "K" — none contain "a". **Bug, confirmed**: queries below ~2 characters silently fall back to the untouched Browse/trending list but the UI still labels it "N shown" as if it were a real result set for that query, with no messaging ("type at least 2 characters", etc.). A reader who searches a single initial expecting a live filter will see plausible-looking but unrelated results and may conclude search is broken or ignoring input.
- No skeleton, shimmer, or spinner was ever observed at any point in this walk (typing, filter apply, pagination) — either results resolve faster than a screenshot round-trip can catch, or there genuinely is no loading state for this path. Cannot distinguish the two with this tool; flagging as **worth checking** against `Skeleton`/`.shimmering()` usage in `SearchModel`/`SearchIdleView`.
- No stale-result flicker was observed across "on" → "one piece" — can't rule it out at finer timing than my screenshot cadence allows.
- Pagination: "one piece" reported "30 shown" initially; scrolling down loaded further pages (screenshots `26`, `27`, `28-pagination-loadmore.png` show doujinshi/anthology results well past the first 30, confirming infinite scroll is functioning), and by the time I scrolled back to the top the count label had updated to **"120 shown"** (`30-top-check.png`) — correct, live-updating pagination count here (contrast with the filter-only "Show N results" preview count discussed in §1/§3, which does *not* match the eventual paginated "N shown" label — e.g. "Show 4,260 results" vs. an actual grid that pages in 30 at a time under a separate, smaller "N shown").
- Tapping a result (`31-detail-onepiece.png`) opens a rich detail page (estimated-next-chapter prediction, "Read in English" deep links to MANGA Plus/Crunchyroll/etc., rating/volume/chapter stats) — genuinely nice, not something I'd call "hand-rolled when the platform provides it"; this looks like real product value.
- Back from detail (`32-back-from-detail.png`): results, query text, and scroll position were all preserved correctly.
- Clearing with the field's `×` (`33-after-clear-x.png`): lands on the idle screen. **Observed, not a bug but worth noting**: browsing "one piece" (typing it and even opening a detail page from the results) did **not** add it to Recent searches. Only after retyping it and submitting with Return did it appear at the top of Recent (`34`, `35-after-clear-post-submit.png`). So Recent only records explicit submits, not "you looked at results for this." Reasonable design, but a reader who typed a query, viewed a detail page, backed out, and cleared the field will not find that query in Recent — possibly surprising since they very much did search for it.

## 3. Power reader: filters, lens, edge-case queries

- Built a compound filter (query "dragon" + Type=Manga chip) via the Filters sheet toolbar button. The Type chip toggles instantly without dismissing the sheet — a properly multi-select filter builder, unlike the single-tap-and-dismiss Tags/Genres pickers in §1. Confirms §1's bug is specific to the Tags/Genres quick-pick path, not the Filters sheet's own chips.
- Save-as-lens: the bookmark icon at the bottom of the Filters sheet is small and easy to mis-tap — two of my first three taps landed on nothing (no visible response, no error) before one connected and opened the naming sheet (`46-bookmark-tap-fresh.png`). This may be purely a tap-target/coordinate issue on my end rather than an app bug (I cannot fully rule that out with this tooling), but the total silence on a miss (no highlight, no haptic implied, no error) makes it hard to tell if the tap registered at all — **worth checking** the hit target size/feedback on that icon.
- The "Save as a lens" sheet (`46`, `47-savelens-confirmed.png`) is well designed: explicit copy — "Lenses sit at the top of Search. This one reruns live — it stores the filters, not the results" — with a "WHAT IT STORES" preview showing exactly `type: manga`. Notably the free-text query "dragon" that was active when I saved is **not** captured by the lens, only the structured filter. This is transparently disclosed in the sheet, so it's a documented design choice, not a hidden gotcha — but a power user building a lens while mid-search might expect the term to come along and should read the preview carefully.
- Saved lens appeared under "Your lenses" on the idle screen with a **live** count ("132,108 now", `54-idle-scrolled-lens.png`) that differed from the value shown at save time in the sheet ("132,108 results" also, consistent here) — confirms the "reruns live" claim is real, not just copy.
- Tapping the lens correctly re-ran the Manga-type filter (`55-lens-tapped.png`). Deleting via "Edit" → red minus (`60`, `61-lens-delete-confirm.png`) worked in one tap with no secondary confirmation dialog — standard, unsurprising, fine.
- Minor, cosmetic: after tapping the lens and returning, iOS's own system "AutoFill" QuickType suggestion chip appeared floating over the results grid (`56-after-lens-back.png`) — this is an OS-level artifact from a text-field focus state, not an app bug, but it visually clutters the top of the results and is worth a glance at whether the search field's keyboard/textContentType configuration is inadvertently inviting it.
- Edge-case queries:
  - `zzzzqqq` (no matches, `62-noresults-zzzzqqq.png`): well-designed empty state — `Nothing matched "zzzzqqq"` / "Try a looser filter, or let the API pick." / a "Random with these filters" CTA. This is genuinely good copy and a real recovery path, worth calling out under Done Well.
  - `a` (1 char): see §2 bug — falls back to unrelated Browse content labeled as if filtered.
  - Leading/trailing spaces (`"  berserk  "`): iOS's own double-space-to-period autocorrect converted the trailing double space to "berserk." (`64-spaces-berserk.png`) — this is a system keyboard behavior, not a MangaBaka bug, and search still matched Berserk titles correctly despite the trailing period, so no functional problem observed.
  - Emoji and Japanese title (ワンピース): **not tested** — the simulator control tool used for this walk can only type printable ASCII ("0 characters typed, N unsupported dropped"). I could not get non-ASCII text into the field at all. This needs a different input method (e.g. pasteboard injection) to test; flagging as a real gap in this walk rather than guessing at behavior.
  - Rotation: not applicable per the brief (no rotation needed) and not tested.

## Summary (10 lines)

1. Simulator/app were fine once pointed at the right UDID; no crashes, no hangs, full walk completed except accessibility tree (tool unavailable) and non-ASCII input (tool limitation).
2. **Confirmed bug**: tapping a Tag or Genre chip directly (the fastest, most obvious path) jumps straight to a broken "0 shown / Nothing matched" results screen, even though the identical filter reached via Filters → "Show N results" works correctly and returns real results.
3. **Confirmed bug**: queries under ~2 characters silently render the untouched Browse/trending grid but label it as if it were live search output ("N shown"), with titles that don't contain the typed letter.
4. Filter/query state (Type chip) can silently outlive clearing the search text, with no badge on the "Filters" button to signal an active filter — a quiet trap, not a crash.
5. Recent searches only record explicit submits (Return), not queries you typed, viewed results for, and even opened a detail page from — reasonable but easy to be surprised by.
6. Pagination, scroll-position preservation, and detail-page richness (estimated next chapter, official reading links) all worked well and felt like real product value.
7. Lens save/run/delete flow works end-to-end and is transparently documented ("stores the filters, not the results"); the save (bookmark) tap target felt unreliable/silent on miss.
8. The empty-results state ("Nothing matched … Try a looser filter, or let the API pick" + Random CTA) is genuinely well designed — best UX moment of the walk.
9. Tags and Genres pickers are inconsistent siblings: Tags has categories, counts, and a search-within box; Genres is a flat uncategorized list with neither.
10. Unresolved: no `inspect` access for the accessibility pass, and no way to type emoji/Japanese through this tool — both need a follow-up with different tooling before the accessibility and CJK/emoji query behavior can be signed off.
